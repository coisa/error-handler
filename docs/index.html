2.x API · PHP 7.4+

Error Handler 2.x

Compose diagnostic reporting, native PHP callbacks and HTTP responses with explicit application boundaries.

The library supplies handlers and PSR adapters. Your application chooses reporters, PSR implementations, callback installation and HTTP emission.

This guide describes the existing 2.x API and compatible maintenance on master. Check your installed version and matching source. A pending Changeset is not a published release.

Installation

composer require 'coisa/error-handler:^2.0'

The package declares PHP ^7.4 || ^8.0. Composer installs PSR interfaces; applications supply concrete dispatchers, loggers and HTTP factories when those integrations are used.

For the runnable recipes, use the cookbook's explicit application dependencies. Resolve them with the actual PHP runtime and retain the application's lockfile.

Start with direct reporting

handleThrowable() delegates to your reporter without installing process callbacks. If the reporter returns, execution continues; reporter failures propagate.

This synthetic reporter prints so its behavior can be verified. Use an appropriate private diagnostic destination in a real application.

Report directly to an application logger

LogThrowableHandler is an explicit opt-in 2.x adapter. Verify that your checkout or release contains it; older installed versions may not provide it. Supply your own PSR-3 logger, optional string level (ERROR by default) and context.

Each call logs exactly getMessage(), including empty, and places the original throwable under exception over any caller value. Other context is preserved without coercion; key order is not a contract. The logger decides supported levels and its failures propagate unchanged, without adapter retries or output.

No automatic discovery or callback registration is added. A private logger is not a public body renderer: keep process logging and the existing HTTP capture/fallback boundary explicit. Read process composition and the complete contract.

Choose the process lifetime

For a whole process, register one handler at bootstrap and leave it active for uncaught exceptions. For a caught operation, report inside its catch and restore callbacks in finally.

Callbacks are process-wide. Use distinct handlers for nested scopes and unregister in reverse order. An unwinding finally runs before the uncaught-exception callback; unregistering there can prevent that handler from seeing the exception.

PHP cannot remove queued shutdown functions. Repeated register/unregister cycles enqueue callbacks. A successfully reported uncaught exception currently exits 0; native compile-fatal reporting observes exit 255 and does not recover execution.

Supply PHP-error policy explicitly

CallablePhpErrorHandler($callback) adapts four unchanged values: code, message, filename and line. Inject the wrapper as the second ErrorHandler argument. The existing constructor remains typed to interfaces; this adapter adds no registration, mask check, conversion, output or automatic discovery.

Callback failures propagate unchanged. The interface returns void: false/null results are ignored and do not restore native PHP fall-through. No fifth error-context argument is supplied. Verify that the selected source contains this additive API, then read the full API contract.

Select diagnostic branches explicitly

FilteringThrowableHandler($reporter, $predicate) evaluates a required boolean predicate once. A match forwards the original throwable once; a nonmatch skips only that delegate. Predicate/delegate failures propagate without retry; non-boolean results raise TypeError. Invert policy in the application's predicate.

This opt-in adapter requires a source version containing the additive API; a pending Changeset is not a published release. It adds no discovery, output, callback registration, recursion guard or response policy. A nonmatch is not recovery or redaction: built-in empty capture still falls back to diagnostic text. See the API guide and HTTP composition.

Attempt every reporter and retain every failure

BestEffortThrowableHandlerAggregate takes a fixed reporter list. Each invocation attempts every slot once, in order, with the same original throwable. Duplicate slots are separate attempts. Zero/all-success passes return normally; any failure, including partial success, produces one AggregateReportingException after all attempts.

The original also remains the previous cause; reporter failures retain their order and object identities. The fixed summary does not make the cause, failures or exception string public-safe. Applications own terminal handling and durable delivery. This opt-in adapter changes no fail-fast default, factory, callback lifecycle or HTTP response policy and adds no retry or reentry guard. Read the full contract and explicit composition.

Keep the existing container boundary

ErrorHandlerContainer accepts an optional application PSR-11 parent. The parent's known services take priority; otherwise library aliases and factories resolve services. The default reporter aggregate is empty and silent, so supply a reporter explicitly.

ConfigProvider retains aliases, factories and Laminas discovery metadata. ServiceManager is an optional application integration, with a version compatible with that application's PHP.

Services are cached. Calling ErrorHandlerFactory explicitly creates a new core handler; a fresh middleware wrapper can still resolve the cached handler. Discovery and construction do not call register().

The container-cause repair preserves the original throwable through factory/alias wrapper chains. The two public exception factories copy integer codes and use 0 for string codes, retaining the original SQLSTATE on the cause. Check the selected source/release and the container guide before relying on this repair.

Select an optional JSON provider

For a source/release containing the optional Interop providers, an application using PHP 8.3+ can install fast-forward/container:^1.9 as its own runtime dependency. Supply PSR-17 response/stream factories and a private ThrowableHandlerInterface reporter, then choose JSON explicitly:

Each provider declares only its own services. Register JSON before the separate base provider so its response alias wins over legacy capture. The JSON profile composes one private report before pure rendering for the existing 2.x middleware. Public JSON is the default. A constructor bool, passed from trusted Config values before container construction, enables development details deliberately; no request header or environment name enables them. Use strict typing and real bool values rather than casting the string "false".

Each factory invocation creates a distinct core handler and middleware. The process alias and directly resolved middleware remain cached; lookup does not register callbacks. The base ErrorHandlerServiceProvider retains legacy capture defaults and requires the application's reporter. The core still supports PHP 7.4 and the legacy container/ConfigProvider. Fresh objects do not remove PHP's existing shutdown-queue limits.

For a required replacement of a library-defined service, combine base, JSON and application definitions in that order in one AggregateServiceProvider; the last definition wins. Separate providers prioritize the first successful resolution. Read the provider guide for complete maps, Config, runtime installation and override semantics. Applications own emission and any reporter output.

Separate HTTP responsibilities

The PSR-15 middleware registers its lifecycle handler, invokes downstream, delegates caught throwables to a response factory and unregisters in finally. It does not independently report before rendering.

The built-in stream factory reports while capturing output. Empty output and the string "0" fall back to the throwable's diagnostic string. A global ThrowableHandlerInterface binding also selects this renderer's reporter: private logging or a filtering nonmatch can leave empty output and trigger that fallback. Keep process reporting and public response construction explicit. The built-in response factory also uses a valid exception message as its reason phrase; a silent or filtered reporter does not create a safe public response.

In a checkout/release containing the reason-phrase repair, CR, LF, NUL, DEL and other forbidden control bytes omit the reason argument so the application's PSR-17 implementation can select its default. Valid horizontal tabs, visible ASCII and opaque high bytes remain unchanged. Empty messages are still passed explicitly, retaining the existing implementation-specific behavior. This prevents an invalid status line; the original throwable, reporting count and diagnostic body fallback remain unchanged.

The application supplies PSR-17 factories, private diagnostic delivery and its emitter. The legacy status policy accepts integer codes from 400 through 500 inclusive; other integers and all string codes, including SQLSTATE, become 500. Use application-owned mapping for domain errors.

For a source/release containing these additive classes, the pure JSON factory returns application/json with {"error":"Request failed"}, preserves integer codes 400–599 and otherwise uses 500. It does not report or capture output. The explicit decorator reports the original once before rendering; reporter failure prevents rendering, and failures propagate after middleware restores callbacks. Use a private reporter that does not print. Defaults remain unchanged.

The optional third boolean defaults to false. An explicit trusted development configuration can enable class/message/file/line and trace metadata, without arguments or objects; debug sets Cache-Control: no-store and replaces invalid UTF-8. Messages and paths still contain diagnostic details. No environment/request autodetection enables it, and the recipe uses a private reporter without output. PHP 7.4 debug use needs the optional JSON extension, included by PHP 8.

See the HTTP guide for success/failure restoration, capture limitations and the complete application composition.
